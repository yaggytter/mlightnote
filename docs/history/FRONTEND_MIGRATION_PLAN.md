# MLightNote フロントエンド完結化 移行計画（案B：TypeScriptへ移植）

| 項目 | 内容 |
|---|---|
| 作成日 | 2026-09-25 |
| 状態 | 段階0〜6 実装済み（ブランチ `feat/frontend-only`）。Go 版は削除し、正解データのみ残した |
| 目的 | 一般公開に向けて、Go API・Docker なしで**ブラウザだけで全機能が動く**静的Webアプリにする |
| 方針 | Go の処理を TypeScript に移植する。移行中は **Go 版を「正解」として出力を固定し、TS 版の出力が完全一致することを自動テストで確認しながら** 部品ごとに置き換える |

---

## 1. 完了条件

1. 今の機能がすべて、サーバーなしで同じように動く。
   - 読み込み：MusicXML／.mxl／MIDI／.mlight。
   - 表示：パート選択、実音表示、略称、パート名ラベル。
   - 再生：反復の展開、カーソル、ループ、テンポ、メトロノーム。
   - 印刷。
   - 編集と元に戻す・やり直す、移調。
   - 保存、.mlight の書き出し、プロジェクト一覧、削除。
2. サンプル楽譜とテスト用楽譜で、**移植版の出力が Go 版と一致する**。
   - 比べるもの：楽譜モデル、表示用 MusicXML、再生データ、インポートレポート。
3. 既存の E2E テストが、サーバーなしの構成ですべて通る。
4. 成果物が静的ファイル（`dist/`）だけになり、静的ホスティングに置ける。
5. 実行時にインターネットへの通信が0件のまま（設計書 §17.4 の要件を維持）。
6. Go のコード（`api/`）と Docker の API サービスを削除し、ドキュメントとデプロイ手順を更新する。

## 2. 移行後の構成

```
今：   画面(React) ──fetch──▶ Go API ──▶ ファイル保存(/data)

移行後：画面(React) ──▶ services/api/*（関数名・戻り値はそのまま）
                          │  postMessage
                          ▼
                     Web Worker（画面とは別スレッド）
                       ├ engine/  … Go から移植した処理（読み込み・採譜・生成・再生データ・編集）
                       └ storage/ … IndexedDB（ブラウザ内の保存領域）
```

- **画面側はほぼ変えない。**
  - `services/api/` の関数（13種類の API 呼び出し）の中身だけを、Worker の呼び出しに差し替える。
  - エラーの形（`ApiError` と、`REVISION_CONFLICT` などのコード）も今と同じにする。
- **重い処理は Worker で動かす。** 大きな MIDI の採譜や MusicXML の解析中も、画面が固まらないようにする。
- **楽譜の描画（OSMD）と音の再生（Web Audio）は今もブラウザ側なので、変更なし。**

### 移植の対応表（`web/src/engine/`）

| 移植先（TypeScript） | 移植元（Go） | Go の行数（本体／テスト） |
|---|---|---|
| `engine/domain/` | `internal/domain`（有理数・音高・移調・楽譜モデル・編集差分・略称・ドラム表） | 1,137 / 434 |
| `engine/importers/musicxml/` | `internal/importers/musicxml`（+ .mxl 展開） | 1,242 / 571 |
| `engine/importers/midi/` | `internal/importers/midi`（SMF・採譜・3連符・調推定・連桁・ドラム） | 1,775 / 951 |
| `engine/exporters/displayxml/` | `internal/exporters/displayxml` | 835 / 447 |
| `engine/playback/` | `internal/playback`（反復の展開・テンポ・強弱） | 633 / 393 |
| `engine/editing/` | `internal/editing`（コマンド・undo/redo・リビジョン） | 364 / 292 |
| `engine/mlight/` | `internal/mlight`（.mlight の ZIP 読み書き・検証） | 384 / 229 |
| `engine/storage/` | `internal/storage`（→ IndexedDB に作り直し） | 412 / 273 |
| `engine/service/` | `internal/httpapi` の業務ロジック部分（13種類の API 相当） | 1,154 / 714 のうち一部 |
| 移植しない | `internal/musicxml/analyze`（Go の検証専用） | 319 / 223 |

### 使うライブラリ（すべて同梱し、CDN は使わない）

| 用途 | 選定 | 理由 |
|---|---|---|
| XML 解析 | **saxes**（SAX 方式・厳密） | Worker の中では `DOMParser` が使えない。外部 DTD やエンティティを解決しないので XXE の心配がない |
| ZIP（.mxl／.mlight） | **fflate** | 小さく Worker で動く。展開サイズの上限を指定でき、zip bomb 対策を今と同じにできる |
| SHA-256 | ブラウザ標準 `crypto.subtle` | 追加ライブラリ不要 |
| ID 生成 | ブラウザ標準 `crypto.randomUUID()` | uuid ライブラリが不要 |
| IndexedDB | ブラウザ標準 API（薄い自前ラッパー） | 依存を増やさない |

## 3. 安全に移すための仕組み：Go 版との一致テスト

「数は合っているのに中身が違う」種類の不具合を防ぐため、**Go 版の出力を正解データとして固定し、TS 版の出力と自動で比べる。**

1. Go 側に、正解データを書き出すコマンド（`api/cmd/oracle`）を追加する。
   - 入力にするテスト用楽譜：`samplefiles/` と `api/testdata/` の楽譜（trio・repeats・notations）。Go 版の削除後は `testdata/` に移した。
   - 出力するもの：楽譜モデル（JSON）、表示用 MusicXML（全パート／パートごと／実音表示）、再生データ、インポートレポート。
   - 編集操作の再現：決まった手順の編集（移調・並べ替え・表示切替・曲情報の変更）をした後の出力も書き出す。
2. ID を決まった値にする仕組みを、Go 版と TS 版の両方に入れる。UUID は毎回変わるため、比較の前にそろえる必要がある。
3. 書き出した正解データを `web/src/engine/__golden__/` に置き、Vitest で TS 版の出力と比べる。
   - 表示用 XML：文字列が完全に一致すること。
   - 楽譜モデル・レポート：内容が完全に一致すること。
   - 再生データ：秒数は 1e-9 以内の誤差で一致すること。
4. Go の単体テストの要点は、Vitest に移す。
5. 正解データはリポジトリに置くので、Go 版を削除した後も一致テストは回り続ける。

## 4. 段階と、各段階の完了条件

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0 準備 | Go 側：正解データの書き出しコマンド、ID を決まった値にする仕組み。TS 側：`engine/` の骨組み、Worker と画面をつなぐ仕組み | 正解データが揃い、Worker 経由の呼び出しが往復すること |
| 1 MusicXML | `domain`、MusicXML の読み込み、`.mxl`、表示用 XML の生成 | XML 系の楽譜で、Go 版と完全に一致すること |
| 2 再生・編集 | `playback`、`editing` | 再生データと、編集した後の出力が一致すること |
| 3 MIDI 採譜 | SMF・採譜の全体 | すべての MIDI で一致すること |
| 4 保存・窓口 | `.mlight`、IndexedDB、`service/`（13種類の API 相当）。レポート画面の直接呼び出しを直し、`.mlight` のダウンロードを Blob 方式にする | サーバーなしで E2E が通ること |
| 5 切り替え | 既定をブラウザ内の処理にする。`persist()` の要求とバックアップの案内。複数タブでの同時編集の検出 | 手動で一通り操作して問題がないこと |
| 6 片付け | `api/` と Docker の API サービスを削除。静的サイト用の `make deploy`。ドキュメントを更新 | 1章の完了条件をすべて満たすこと |

**作業量の目安：** およそ 2〜3週間分（テスト移植を含む）。

## 5. 利用者から見て変わること

| 項目 | 今 | 移行後 |
|---|---|---|
| 必要なもの | Docker（サーバー） | ブラウザだけ |
| 曲の保存場所 | サーバーのディスク | そのブラウザ内（IndexedDB） |
| 別の PC・ブラウザで続きを開く | 同じサーバーなら可 | `.mlight` で持ち運ぶ |
| データが消える可能性 | ほぼなし | ブラウザのデータ削除で消えうる。消されにくくする設定を要求し、バックアップを案内する |
| セキュリティ | サーバーで他人のファイルを処理する | 処理はすべて本人のブラウザ内。サーバー側の攻撃対象がなくなる |

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| 移植で内容がずれる | 3章の一致テストを、各段階の完了条件にする |
| 小数計算の差 | 楽譜上の時間は有理数で計算する。秒への変換だけ小数で、誤差 1e-9 以内を合格とする |
| 巨大なファイルや壊れたファイルで固まる | 処理は Worker で行い、上限は今と同じにする |
| ブラウザの保存データが消える | `persist()` の要求と `.mlight` バックアップの案内 |
| Worker では DOMParser が使えない | saxes を使う |
| 2つのタブで同時に編集 | BroadcastChannel で変更を知らせ、古いリビジョンからの編集は今と同じく衝突として扱う |

## 7. 今は変えないもの
- 画面のデザイン・操作・ショートカット。
- `.mlight` の形式（サーバー版で保存したファイルをそのまま読める）。
- 楽譜の描画（OSMD）と再生エンジン。

## 8. 決めること（実装での既定）

| 項目 | 実装での既定 | 備考 |
|---|---|---|
| 公開先 | 未定。静的ファイルの確認は nginx の静的コンテナで行う（`make deploy`） | 決まり次第、ホスティング先に合わせて CSP の指定方法を変える |
| PWA | 今回は入れない | 後で追加できる |

| Go 版を消す時期 | 段階6（このブランチの中）で削除する | 正解データは残るので、一致テストは続けられる |

## 9. 実施結果（段階0〜6）

- 一致テスト：全8曲で、楽譜モデル・レポート・表示用 XML（1バイト単位）・再生データ・編集の再現が Go 版と一致。Go 版で保存した `.mlight` 5件も開けることを確認。
- 移植中に Go 版の不具合を1件見つけた：並び順が非安定ソート（`sort.Slice`）に左右され、同じ MIDI でも実行ごとに出力が変わりうる箇所が2つあった。安定ソートに直してから正解データを作った。
- 「保存」の意味：編集ごとに IndexedDB へ書き込むので、保存は「保存済みのリビジョン」の記録だけを行う。サーバー版が作っていたスナップショットの `.mlight` は作らない（ダウンロード時にその場で作る）。
- サーバー版のデータ：Docker のボリューム（`mlightnote-data`）に残っているプロジェクトは、新しい版には自動では移らない。必要なら `main` をデプロイして `.mlight` をダウンロードし、新しい版で読み込む。
- 正解データの扱い：`web/src/engine/__golden__/` は固定。意図して挙動を変えるときだけ、同じコミットで書き換えて理由を記録する（CLAUDE.md）。
